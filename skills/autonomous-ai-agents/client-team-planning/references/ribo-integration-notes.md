- Files Robi sends land under `~/.hermes/profiles/<profile>/cache/documents/native-inputs/<hash>/`. `read_file` extracts a PDF with a text layer; for a long YAML-as-PDF run `pdftotext -layout <pdf> <scratch>/x.txt` and grep. Say plainly that you read extracted PDF copies, not the source files, and did not run a validator; ask the vendor for the real YAML if a validator run is needed.
- Checks that need no validator: count `operationId:` and compare the list with the spec's endpoint list (grep the operationIds, because path lines wrap in a PDF and awk on them misses routes); confirm no operation can change autonomy, approve knowledge or training, or sign off readiness (only a GET for readiness); the provider enum holds only the approved provider; the idempotency header is referenced on every write; a counts-only secret-pattern scan over every document finds nothing but placeholders. Never paste a found secret into chat.
- Every entry condition the vendor lists (sandbox exists, local env no longer points at production, dev database confirmed) is a stop sign for Phase 3: say which are unmet and that nothing connects or reads data until they are.
- The vendor's disclosure of its own writes to production (session rows from a demo sign-in) is the owner's decision, not the engineer's: summarise it, list the read-only checks and the password change it suggests, and do not touch RIBO.
- Hermes-side gaps the spec assumes and nobody has built; raise each with Robi before planning Phase 3: (1) agents have no tool that can call an API, so plan ONE small connector script, built and tested by a developer (the engineer writes no production code), that holds the per-role client secrets in the OS keychain and does the polling, heartbeat, lease renew/release, event-cursor storage and write-back, while the helpers only read and write files and never see a token; (2) polling and heartbeats need an always-on process and a Mac that stays awake, which needs Robi's separate OK because the engineer may not create timers or schedules; (3) the heartbeat proves the connector is alive, not that a model is working, and `configured_providers` should be read from each profile's real config; (4) an erasure event obliges Hermes to purge local copies: real prospect data would sit in Work/ files, each helper's session history, memory notes and logs, and nobody can delete files today, so design the purge and a log-retention limit before any real data flows.

# Revising a validated client team into a reusable product (migration and architecture v2)

Use when the owner changes direction on an existing, tested team (e.g. one client's SDR team becomes a reusable agent where that client is only the first configuration) and wants the old work kept.

## Procedure (planning and audit only; nothing built, registered, connected or changed)
1. Inspect real files, read-only, in one batch: registry rows and test records, the team manifest, every member's profile (SOUL size, config.yaml toolsets), the generic briefs and index, `Agents/skills/`, the project's plans, and the test reports. List what you could NOT inspect (code outside the engineer's folder, the vendor's codebase) and tag those claims unverified.
2. Snapshot the evidence BEFORE any re-check: copy test reports, member briefs, backups, manifest, registry, run outputs, Memory/ and Team/ into `Work/<Product>/evidence-<date>/`, write `SHA256SUMS.txt` (run `shasum -a 256` from inside that folder) and verify with `shasum -a 256 -c` (0 mismatches). `check_agent.py` overwrites a report and the registry test string each run, so the snapshot is the only record of earlier pass counts. Live run outputs sit in the project's Work/, not in the archive folders: copy them too.
3. Search for existing reusable assets before proposing any agent: `GENERIC-HELPERS.md` rows added since the last plan (an onboarding/discovery interviewer already covered most of an ICP-discovery function), the skills library, and the old generic briefs whose method text can feed skills.
4. Classify each component as DONE (built and tested), PART, MOD (reusable with modification), MISSING, BLOCKED, and map every existing member to a new role. Default answer for each new 'subagent function': a versioned skill on an existing member, not a new agent.
5. Write one plan file in a new folder `Work/<Product>/` (do not touch the old plans, manifest or registry; do not register a new project): current vs proposed diagram, mapping table, skills table, integration contracts, UI and backend requirements, roadmap, blockers, costs and usage controls, acceptance criteria per phase, migration and rollback, numbered decisions with the recommended answer first. End the chat reply with ONE question: approve the direction with the recommended answers?
6. After approval, write a HANDOVER.md that splits work by owner (see below) and log it in the engineer's CHANGELOG.

## Design rules that held up
- 'Subagents' in Hermes means two different things: temporary delegation sub-agents (no own memory, folder or registry row, inherit the lead's tools) and separate profiles (own memory, tools, checks). Anything that stores or touches a client's data, or needs its own tool permission or independent check, must be a profile. Pure reasoning methods become skills.
- Methods (ICP, BANT/CHAMP/MEDDICC/SPIN, ABM, buying signals, nurturing, analytics) are skills; paid or credentialed tools (a data-discovery provider, mail) are deterministic and belong in the external system's backend with budgets, dedupe, source tracking and policy gates. The agents hold no tokens; the system of record holds provider and mailbox credentials, runs approved actors only, stages candidates before they enter the CRM, and enforces caps and opt-outs at send time.
- Client-agnostic means no client name inside any generic definition or skill; the client comes from the project folder and the task. Client ICPs, weights, playbooks and knowledge live in the system of record, never in a skill.
- Per-client isolation = one team copy per client while helpers are stateful. Hermes facts confirmed by agent-creator: skills named in a brief load on demand (only a short index is in the prompt, so moving method text into skills should shrink prompts, unmeasured), and every one-shot call (`hermes -p <slug> -z`) persists a session row in that profile's own state.db with no switch to skip it (pruning exists but only deletes afterwards). So a shared pool of stateless specialists across clients is not possible; history stays per profile. Count this in erasure and retention design.
- Primary SDR identity: a new generic definition derived from the approved team-lead (generic team-lead untouched), keeping the lead separate from writers and reviewers. Its ICP gate and budget gate use fixed refusal phrases and only a person's approval (his message or a file naming him and the date) opens them.
- Costs: never invent prices. Give the cost lines, how each is measured in the sandbox, and the controls (per-tenant and per-run caps, alerts at 50/80/100 percent, approval before each paid run, enrich only qualified leads, dedupe before enrichment, auto-pause on bounce or complaint thresholds). Say that no budget can be set from the plan.
- Compliance: scraping and enrichment need counsel review of provider and target-site terms and privacy law before any production run; you have verified none of it.

## Who does what (handover)
- Agent Creator owns the repository: skills (Agents/skills/<name>/SKILL.md with a version field), generic definitions and new generic versions (old text archived as `<id>-v<n>-archive.md`), the index. The engineer may send it ONE background request, and only for a missing generic helper (e.g. the primary lead). A skills library or new versions of existing generics is NOT a request the engineer may send: write the list in HANDOVER.md and hand Robi a paste-ready message to give agent-creator himself. Include in the one request the technical questions you need answered (skills loading, session persistence) and tell it not to run check_agent.py on live generics.
- The engineer assembles client teams: copy briefs pinned to the new versions, dry runs, `--update` per member with backups, full checks compared with the snapshot (no member's pass or scenario count may drop), manifest, team template, onboarding checklist, repeat of the synthetic run with the same fixtures.
- The vendor's AI developer builds the connector; the vendor's team builds the platform. The engineer neither inspects nor runs their code.
- Robi approves each phase; autonomy level 2 comes last and only on his explicit decision.

# Client team planning (Team-Workspace / Agents repository)

Class of task: Robi asks for a team of helpers for one client or project. Output is a short plan, then paperwork, then (only after separate yeses) builds. Never build, connect tools or create timers in the planning pass.

## 1. Inspect first (read-only, batch the calls)
- `Agents/briefs/GENERIC-HELPERS.md` (index only; not a registry mark; only roles in its generic table may be copied)
- `/usr/bin/python3 Agents/bin/registry.py status` and `hermes profile list`
- `Agents/SCHEMA.md` (team manifest section) and an existing `Agents/teams/*.yaml` as a model
- Briefs of candidate roles (check for client data before any copy): team-lead, memory-manager, document-engineer, reviewer, sales-agent, etc.
- `Agents/registry.yaml` `clients:` list: is the project already there?
- Existing helpers are files-only (no web, no outside tools, no timers) and in `testing`. Any tool/timer is a separate step needing its own OK; `create_agent.py` never connects tools or makes timers.

## 2. Decide the architecture, and say why in the plan
- State deterministic vs single vs multi-agent and judge on capability, quality, reliability, coordination complexity, cost. Never default to a number.
- Start from team-lead + memory-manager + document-engineer, then add roles only for a stated problem.
- Split members by tool permission (least privilege) and by who checks whom. A tool (Apollo, Apify, email, calendar, a CRM API) is never a member; it is granted to named members.
- Reuse before creating: a generic helper becomes a modified COPY brief (generic untouched). If the generic has its own sub-helpers, remove them in the copy when the team lead already splits work.
- Roles not in the index are "missing": request them from agent-creator, never write them.
- Reports/analytics: prefer extending document-engineer (each line cites its source) over a new analyst member; note a later merge/split review.
- Per-client isolation needs separate profiles with their own memory (Hermes delegation sub-agents have none); methods that only need reasoning become versioned skills on existing members, not new agents.

## 3. Deliver the plan (Telegram)
Short, plain words, no tables: ASCII diagram in a code block, then bullets for members (existing / modify / missing / not reused with reason), tool matrix, workflow, autonomy and escalation, isolation, recovery, phases. End with exactly ONE question. Ask the one question that most changes the design first (e.g. tenancy model). Save the draft to `Work/<ProjectFolder>/PLAN.md`.

## 4. Phase 0 paperwork (after a clear yes to that scope)
1. Confirm project folder name and base before anything is created; a client name given alone is not a yes. Follow the registry convention: CamelCase project + short lowercase base (e.g. FeldcareConnects / feldcareconnects).
2. `new_project.py <Project> <base> --dry-run`, read the plan, then `--approved`. It creates the folder, 14 files and the registry client; no agents. Create `Work/<Project>/` only with the final name (avoid renaming later).
3. Write `Agents/teams/<Project>.yaml` with `lifecycle: proposed` (schema v2: reasoning, members with definition_id, planned_instance, `instance: null`, depends_on, responsibilities, handoff; approval_boundaries). Put the autonomy/escalation/tool rules in approval_boundaries. List members in dependency order: `validate_registry.py` builds its member index while iterating, so a `depends_on` naming a member listed LATER gives `E-team-invalid-dependency` (hidden while that member was still missing). Reorder the entries; keep a backup copy first.
4. Run `validate_registry.py | grep <Project>`. Missing-role members give `E-team-missing-agent` until agent-creator builds them; that is expected, report it as such.
5. Draft TEAM-MAP.md and SHARED-BRIEF.md in `Work/<Project>/`. The project `Team/` folder is not created by scripts, so do not hand-write there; place them after the build is approved.
6. Missing roles: ONE request per role via `hermes -p agent-creator --in /Users/robi/Team-Workspace/Agents -z "<request>"`. Include role, why, team context, needs, tools it will use later (marked as separate OK, not in the brief). No client data. Run independent requests in parallel with a generous timeout.
7. Tell Robi: "I sent the request. Please open agent-creator to approve it." Relay the assumptions agent-creator asks him to confirm. If Robi replies "I approved, do it for me", still never relay or proxy the approval (it must be given in agent-creator's own chat, and a background call cannot build): hand him one paste-ready message for agent-creator (build the named roles as written, show the check results, then add them to GENERIC-HELPERS.md). When he later says to check the build, verify read-only: `ls briefs/<role>*`, the brief's `Status:` line, `grep -c definition_ briefs/<role>.md`, `registry.py status`, `registry.py find --generic`, the index rows, `validate_registry.py`. Roles may already be `production` because Robi promoted them in agent-creator; report it and ask only if it looks unintended.
8. Append one line to `Multi-Agent-Engineer/CHANGELOG.md` (`- [YYYY-MM-DD] [multi-agent-engineer] what — detail`).

## 4b. Copy briefs and pins (learned in the COB team)
- A copy brief pins `source_definition: <id>@<version>`; the generic brief must carry `definition_id` + `definition_version` or the build fails at `--dry-run`. Check with `grep -n definition_ Agents/briefs/<role>.md` BEFORE planning. Fix only through agent-creator (metadata-only, Robi's yes); verify with `diff` against a scratch copy of the old brief.
- `check_agent.py <generic-slug>` (even without --scenarios/--update) overwrites that live helper's registry `tests` field and its `-test-report.md`. Warn agent-creator not to run it on a live generic/practice helper unless Robi accepts losing the scenario record; a recovery needs `--scenarios` against the live helper.
- `create_agent.py <brief> --dry-run` works while the brief says `Status: DRAFT` (approval is checked only with --approved). Slug = `<client-key>-<name>`, e.g. cobcorporationglobal-team-lead. Build order: members the lead hands to first (memory-manager, document-engineer), team-lead last.
- ALWAYS pass the brief to `create_agent.py` as an ABSOLUTE path (even from inside Work/<Project>/). The registry row stores the path as typed; a relative one makes `check_agent.py` (which runs from Agents/) report `FAIL brief: no brief on file` and skip the brief's own tests, running only 3 generic scenarios. A "scenarios 3/3 pass" beside a FAIL is not a pass. Repair is `create_agent.py <absolute brief> --update --approved` (backs up first), which counts as a change to an existing member: ask Robi first; never hand-edit registry.yaml. The verified-good order is: dry-run -> `--approved --smoke` -> `check_agent.py <slug> --scenarios` and confirm the report lists the brief's own test names.
- Approving a brief and approving its build are two separate yeses ("Go" after a brief review means approved briefs only). Ask for the build yes per member or per named batch, stating the order, and never build the member that depends on unbuilt ones (team-lead) in the same yes.
- Marking a brief approved: replace only its `Status:` line with `Status: APPROVED by Robi on <date>`, then re-run `--dry-run` to confirm it still passes.
- check_agent --scenarios can leave real practice files in the project (e.g. Work/reports/test-report-draft.md, Work/escalations/ESC-001-*.md). Tell Robi; the engineer cannot delete files outside its folder by hand.
- Pin fixes for several generics at once (reviewer, sales-agent, team-lead all lacked `definition_id`/`definition_version`): send ONE agent-creator request per fix batch that says: metadata-only (generic, definition_id, definition_version, capabilities), pick the version the history supports (a brief that says 'v2' pins 2 when v1 text was never archived), and do NOT run check_agent.py or --update on the live generic helpers. Verify yourself: `diff` against scratch copies of the old brief, registry.yaml and test report unchanged, `validate_registry.py` counts identical. Ask it to say which `definition_version` the history supports and whether an `<id>-v<n>-archive.md` exists for the older version (the resolver reads that exact name, not `-prev-archive`); a missing archive must be a byte-for-byte copy of the real old text, checked with `cmp`, never rewritten from memory. Every newly built generic needs this check: a role can be built and approved yet still lack `definition_id`/`definition_version`.
- One-time manual deletion of leftover practice files (no script deletes, and helpers may not): name the exact paths and say it is a manual exception, get an explicit yes to that list, delete only those (leave README.md and empty folders), and log it in the engineer's CHANGELOG.
- Never hard-code 'who is built' in the team-lead copy. Make it read the 'Built now' list in Team/TEAM-MAP.md each time, and update that list (project copy and Work copy) whenever a member is built, or the lead refuses newly built members. Changing an approved copy brief later: save the old text beside it (`<brief>-before-<date>.md.txt`), patch the brief, run `create_agent.py <abs brief> --update --dry-run`, show Robi the changed lines, wait for his yes, then `--update --approved` and `check_agent --scenarios`. For a bundle across many members, generate the edits with one scratch script (backups into one `before-update-<date>/` folder, diff each build-spec to prove only the intended lines changed), set the Status line to `DRAFT UPDATE (not approved)` while waiting (the registry points at this file, so a stale APPROVED line would misstate it), dry-run every member, and only after the yes set the Status back to APPROVED, apply all `--update --approved`, then run `check_agent --scenarios` for all members as ONE background job (`terminal(background=true, notify=true)`, about 3 minutes per member) and poll with `process_manage wait` (waits clamp to 180s). Placing an updated Team/ file in the project is another one-time manual copy that needs Robi's yes.
- Every member copy must say to read Team/SHARED-BRIEF.md, use the same six-field task header (Tenant, RIBO ID(s), Knowledge version, Autonomy level, Environment, Idempotency key), and the lead's task Output must name the owner's standard output path rather than invent a file name or length. Otherwise the reviewer marks header and file-name checks NOT MET in the end-to-end run.
- Copy brief tests must be self-contained: every scenario is a fresh chat, so 'same task as above' fails, and a made-up 'good' sample must really meet its own task (line breaks, no extra offers). In test mode helpers still sometimes save real files; tell the test to 'show here, do not save a file'.
- Narrowing a generic into a role copy (e.g. sales-agent -> lead-qualifier): list what is kept, removed and added in the brief's change section, drop sub-helpers/delegation and sample leads, and flag any deviation from the approved plan (e.g. dropping a layout) in the chat message.
- Copy briefs of already client-ready generics (prospect-researcher, sdr-conversation-agent, readiness-trainer): generate them with a small script in the scratch dir from the approved generic build-spec (placement -> client:<Project>, folder path swap, add `source_definition: <id>@<ver>`, drop generic/definition_id/definition_version/capabilities/requires, replace the 'This is the generic' context line, add one RIBO-ready header instruction), then diff each against its generic to prove only those lines changed and that the test count matches. Build order: researcher, trainer, then conversation agent last. Scenario runs of these leave dozens of practice files in Work/ (research, conversations, training, simulations): list them and ask before one-time deletion.
- Teams that will see personal or prospect data: put `fallback_providers: none` in every copy brief (a scalar key, placed right after `source_definition:`). The factory's `Agents/fallback-policy.yaml` default chain is added to every NEW build, and `--update` never changes an existing chain unless the approved brief names a chain or `none`, so the key must stay in the briefs permanently. Preview the exact before/after without touching the real brief: copy the brief into the scratch dir, add the key, run `create_agent.py <scratch copy> --update --dry-run` and read the `fallback_providers: CHANGE requested` line. Then back up the briefs, add the key to all members, dry-run each, get the yes, `--update --approved` each, confirm `grep -c fallback_providers ~/.hermes/profiles/<slug>/config.yaml` is 0 for every slug, and re-run `check_agent --scenarios` as one background job. Only the named client's profiles change; generic and other-project profiles keep their chains. Explain the trade-off in plain words: with no backup, an outage of the main AI service makes the helpers stop and wait (safe when the external system holds the queue), instead of prospect text reaching other providers.
- Hermes facts verified by agent-creator/me on this Mac (v0.23.1): every one-shot call (`hermes -p slug --in dir -z`) writes a session row to that profile's own state.db and no flag skips it, so a shared stateless pool across clients is not possible and per-client team copies stay the isolation model; skills named in a brief load on demand (only a short index is in the prompt); profile config is YAML (`config.yaml`, `model.provider`).
- Copy brief template: take the Lighthouse copies (Work/Lighthouse/) for the memory-manager and document-engineer pattern; for team-lead replace practice wording with 'built members only' + team map.

- When Robi says he is getting lost, asks 'where are we' or wants an overview, answer once with a layered snapshot in plain words and no tables: goal in one line, what is built and tested, what is not built, what is in progress and unverified, what blocks it and who owns each blocker, what he personally owes, what he can change safely. Do not re-list history; then ask what he wants to change. If he repeats the question, shorten, do not repeat.
- When he says 'you decide', decide only reversible, low-risk design choices (a read-only flag, an alert destination, wording kept from an approved brief); record each in the working file and in the chat with its scope and say it approves nothing else. Never decide approvals, builds, connections, timers, credentials, privacy or autonomy gates for him.
- When he asks 'provide it again here', paste the full text inline in the chat (and name the file); a file path alone is not an answer.
- Robi often answers one word ('Ok', 'Go', 'Yes') and is a newbie: write plain words, one yes/no question per step, and state exactly what the yes covers. Avoid either/or questions: a bare 'Ok' or 'yes' to one is ambiguous. If one slips through, do nothing irreversible; re-ask with clickable choices (clarify), and if clarify times out repeat the options in text and wait. When the answer is clear enough to proceed with the first-listed option, say which interpretation you took. If he says he does not understand a question, restate it in four plain parts (what it is, why it matters, the two choices, my recommendation), then ask the yes/no again. A yes to approve briefs is not a yes to build them.

## 5. Later phases (each needs its own plan + yes)
Build defaults with `create_agent.py <absolute brief path> --dry-run`, then `--approved --smoke`, then `check_agent.py <slug> --scenarios`; claim "works" only with no FAIL for every member. The team manifest cannot reach `lifecycle: approved` while any member's definition (e.g. a missing role still pending in agent-creator) has no approved brief, so leave it `proposed` and only record built `instance:` names, with Robi's yes. Once every member is built with 0 FAIL, the synthetic run (see below) passed review and Robi says yes, move it to `validated` in one edit: back up the file, set `lifecycle: validated` with an `approval:` note citing his approvals, add `definition_version` pins for members that lacked them, refresh the stale header comment, then run `validate_registry.py` (expect 0 errors). Never set `active`: that needs a separate activation OK and a real result. Say plainly that `validated` is not production and nothing is connected. Connect tools one at a time, read-only first. `run_team.py` (Hermes Kanban) is the deterministic coordinator for executing a team manifest. Monitoring the running team belongs to the project-manager helper, not here. When Robi asks the engineer to execute the end-to-end test run (even offering "authority"), decline once, then write a user-run script and step sheet and read the result afterwards: see `references/synthetic-end-to-end-run.md`. Do not delete the practice files it leaves without a listed-paths yes.

See `references/teardown-and-cleanup.md` when the owner asks to remove or start fresh on a built team (retire order, what the engineer cannot delete, blocked-approval fallback script), `references/reusable-product-migration.md` when the owner changes direction on an already validated team (audit, evidence snapshot with hashes, existing-to-new mapping, skills vs agents, who does what with agent-creator), `references/crm-backed-sales-team.md` for the pattern used when a CRM is the source of truth and the team talks to outside people, and `references/ribo-integration-notes.md` for the RIBO status, how to review the vendor's returned spec PDFs (checks, Hermes-side gaps: connector, always-on process, erasure), what blocks Phase 3 and the first-slice order.
